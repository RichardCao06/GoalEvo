> **文档状态**：默认适用的项目工作准则。涉及研究目标、规范性边界、主要假设、风险接受、密封测试和对外结论的条款，必须由人类项目负责人明确批准后冻结。任何偏离均应形成书面 Amendment，而不得通过聊天、代码或提示词中的隐含修改生效。

# 1. 文档目的与适用范围

本宪章用于规范人类研究者与 AI Agent 在 **Goal-Governed Self-Evolution / 目标治理自进化**项目中的共同研究、软件开发、实验运行、数据分析和成果发布行为。

它适用于：

- 研究问题形式化、变更分类、H1–H3 假设与数据结构；
- Track A 受控 Benchmark 的世界、Oracle、Harness、Evaluator 与实验平台；
- Track B LCA 案例、证据包、专家盲评和真实领域验证；
- 代码、配置、提示词、数据、统计脚本、论文和开放科学材料；
- Builder Agent、Red-Team Agent、Audit Agent、Experimental Agent 等不同 Agent 角色；
- 人类项目负责人、方法与统计负责人、领域负责人、数据负责人和独立保管人。

本宪章的目标不是最大化自动化率，而是建立一种可追责、可复现、可审计、可反驳的人机合作方式。

# 2. 宪法级总原则

## 2.1 按决策权分工，而不是按“谁更聪明”分工

- **人类保留规范性决定权和最终责任**：决定研究追求什么、什么不可接受、谁有权批准、哪些风险可以承担以及结论如何对外表达。
- **Agent 承担认知扩展和规模化执行**：生成候选、反例、边界案例、形式结构、代码、测试、模拟、文档和一致性检查。
- Agent 的建议可以优于单个人类判断，但“建议更好”不自动等于“获得授权”。

## 2.2 目标、权限、证明和能力必须分离

不得把以下对象混为一个“总分”或一个可自由改写的提示词：

- **Goal Contract**：什么结果才有价值，哪些结果绝不能接受；
- **Autonomy Contract**：系统可以自主做什么，哪些操作需要批准；
- **Assurance Contract**：凭什么相信结果、由谁独立检查；
- **Capability Envelope**：系统在哪些任务范围内经过证明可靠。

## 2.3 提出、执行、评价、批准不得由同一主体独占

任何主体，无论是人还是 Agent，均不得独自完成以下完整闭环：

> 定义成功标准 → 修改系统或标准 → 评价修改 → 批准修改 → 宣布成功

关键规范变化必须具备角色隔离和独立审查。

## 2.4 可逆、可验证的任务提高 Agent 自治；规范、高风险任务提高人类控制

Agent 自治程度随下列条件增强而提高：

- 任务边界明确；
- 修改可逆；
- 有自动化测试或确定性 Oracle；
- 影响范围有限；
- 全程可记录和重放。

人类决定权随下列条件增强而提高：

- 修改“什么算成功”；
- 扩大权限或降低证明要求；
- 涉及高风险、伦理、数据权利或对外发布；
- 修改确认性假设、主要指标、Gold 标签或密封测试；
- 后果难以回滚。

## 2.5 证据优先于流畅解释

- Agent 不得用语言自信代替证据。
- 人类不得因输出表达流畅而降低验证要求。
- 可由程序判定的事项，优先由固定程序判定；需要专业判断的事项，采用独立、结构化、可记录的人类评审。

## 2.6 失败必须被保留

方法失败、被拒绝 Patch、回归、超预算、严重 False Pass、专家分歧和密封测试不支持均属于研究证据，不得因不利于主张而删除、隐藏或改名。

# 3. 规范性用语

本文件中的条款按以下强度理解：

- **MUST / 必须**：强制要求；违反即构成流程缺陷或需要正式豁免。
- **MUST NOT / 禁止**：不可执行；如确需改变，必须修改本宪章或相关协议。
- **SHOULD / 应当**：默认要求；偏离时必须记录理由、风险和补偿措施。
- **MAY / 可以**：可选做法，由任务条件决定。

# 4. 人类角色与最终责任

## 4.1 人类项目负责人（Research Owner）

最终拥有：

- 研究问题、范围与核心主张；
- Goal Contract 和不可妥协红线；
- 主要里程碑、论文结论和对外发布；
- Protocol Freeze 与 Amendment 的批准权；
- 在角色冲突无法解决时的最终治理责任。

不得独自同时担任密封测试保管人和最终成功裁决者。

## 4.2 方法与统计负责人（Methods / Statistics Lead）

最终拥有：

- Estimand、主要比较、样本设计和统计模型；
- H1–H3 的主要终点与支持/否定条件；
- 非劣界限、排除规则、缺失数据和失败运行处理；
- 确认性与探索性分析的边界。

## 4.3 领域负责人（Domain Lead）

最终拥有：

- 领域目标、对象、边界和风险语义；
- 变更分类中的规范性边界；
- 什么构成严重 False Pass；
- 谁具备何种授权；
- Track B 专业判断、代理数据和建模可用性的解释。

## 4.4 数据负责人（Data Steward）

最终拥有：

- 数据字段的现实语义和数据生命周期；
- 权限、隐私、版权、脱敏和公开范围；
- Schema 版本、迁移和数据完整性规则；
- 原始事实、派生标签和人工裁决之间的区分。

## 4.5 独立保管人 / 审计人（Independent Custodian）

最终拥有：

- Sealed Test、隐藏目标、Gold 标签和冻结哈希的隔离管理；
- 访问日志与解封时点；
- 对协议冻结、主实验运行和结果重算的独立检查。

# 5. Agent 角色与隔离要求

## 5.1 Research Builder Agent

负责候选形式化、Schema、代码、测试、模拟、文档和工程实现。

限制：正式冻结后，不得根据主实验结果自行修改协议、指标或 Gold 标准。

## 5.2 Red-Team Agent

负责攻击定义和方法，包括：

- 构造反例、边界案例和规避策略；
- 发现循环定义、指标操纵和弱基线；
- 寻找通过弃权、弱化评价器、扩大权限或修改分母制造表面改进的路径。

限制：不得批准自己提出的修订。

## 5.3 Audit Agent

以只读方式检查：

- 协议、代码、数据与统计脚本的一致性；
- 结果是否可从原始轨迹重算；
- 是否发生隐藏目标、Gold 标签或密封测试泄漏；
- 是否存在未记录的配置、模型或提示词变化。

限制：不应与 Builder Agent 共享未隔离的工作记忆；关键结论必须有程序或独立人类复核。

## 5.4 Experimental Agent

是被研究对象，负责处理任务、诊断失败和提出 Patch。

禁止访问：

- 隐藏真实目标；
- Gold 分类标签；
- 密封测试；
- 独立审计结论；
- 其他方法组结果；
- 为攻击其行为而专门设计但尚未公开的测试。

# 6. 决策权与 Agent 自治等级

## 6.1 自治等级

| 等级 | 定义 | 典型任务 | 人类要求 |
|---|---|---|---|
| A0 建议 | Agent 只分析和提出候选 | 研究目标、风险接受、非劣界限 | 人类决定 |
| A1 草拟 | Agent 生成可编辑草案 | 形式化、Codebook、统计方案 | 人类逐项审查 |
| A2 沙箱执行 | Agent 可实现和运行，但不能进入正式分支/数据 | Schema、验证器、Fixture、模拟 | 结果可回滚，完成后审查 |
| A3 受控执行 | 在冻结规范和测试保护下执行低风险修改 | 文档、测试、非关键代码、重复实验 | 自动 Gate + 事后抽检 |
| A4 正式生效 | 修改进入正式协议、主分支、正式数据或发布 | 合并、部署、协议冻结、主实验解封 | 必须由有权人类批准 |

**默认规则**：没有明确授权时，Agent 最高只拥有 A2；已经冻结且由测试保护的重复性任务可预先授予 A3；规范性和正式发布类任务永远不得由 Agent 单独获得 A4。

## 6.2 决策权矩阵

| 决策 | Agent | 人类负责人 | 独立审查 |
|---|---|---|---|
| 生成候选形式化和反例 | 主责 | 评价与选择 | 建议抽检 |
| 决定研究价值与核心问题 | 建议 | 最终决定 | 方法负责人复核 |
| 定义变更分类语义 | 生成与攻击 | 最终决定 | 双人编码/裁决 |
| 编写 Schema、验证器和测试 | 主责 | 语义验收 | Audit Agent / CI |
| 修改 H1–H3 或主要指标 | 只可提案 | 项目与统计负责人批准 | 必须 |
| 设置非劣界限与安全阈值 | 模拟与敏感性分析 | 最终决定 | 必须 |
| 运行开发/试点实验 | 可执行 | 监督 | 日志审计 |
| 解封密封测试 | 禁止 | 独立保管人 | 双人授权 |
| 删除失败运行或排除数据 | 禁止自行决定 | 按预注册规则决定 | 必须记录 |
| 对外发布结论 | 起草 | 人类作者负责 | 证据与措辞审查 |

# 7. 标准协作生命周期

每项非简单任务应按以下流程进行。

## 7.1 工作单定义

人类或 Agent 建立 `Work Order`，至少包含：

- 任务编号；
- 目标与非目标；
- 已知约束；
- 交付物；
- 验收标准；
- 风险等级；
- Agent 自治等级；
- 需要的人类决策点。

对于可逆且边界清楚的技术任务，Agent 应直接开始，不应反复要求确认。对于规范性歧义，Agent 必须明确升级。

## 7.2 候选生成

Agent 应在存在实质选择时生成多套有差异的方案，而不是把第一套输出伪装成唯一答案。候选方案必须说明：

- 优点和代价；
- 假设；
- 风险；
- 所需数据；
- 可证伪条件；
- 推荐方案及理由。

## 7.3 对抗审查

Red-Team Agent 或独立人类应尝试证明方案不成立，重点检查：

- 是否混淆目标、评价器和能力；
- 是否存在自评或循环证明；
- 是否可以通过修改分母、弃权或弱化规则钻指标漏洞；
- 是否因基线过弱而预设结论；
- 是否缺少失败、回归和历史失效处理。

## 7.4 人类决策

涉及规范、责任、风险或研究主张的事项，由有权人类签署 `Decision Record`。决定必须包含被拒绝方案及理由，避免结果不理想时事后切换解释。

## 7.5 Agent 实现

Agent 按批准方案编写代码、Schema、测试、文档和迁移，不得扩大范围。遇到范围外问题时，应：

1. 暂停受影响部分；
2. 完成不受影响的可逆工作；
3. 提交最小化升级包，而不是隐含自行决策。

## 7.6 独立验证

验证优先级：

1. 确定性程序；
2. 属性测试和重放；
3. 独立 Agent 审计；
4. 独立人类审查；
5. 专家裁决。

不得只用“另一个 Agent 认为合理”替代验证。

## 7.7 冻结、交付和追溯

正式交付必须包含：

- 修改内容；
- 未修改内容；
- 测试与结果；
- 已知限制；
- 文件、版本和哈希；
- 风险和回滚方式；
- 未解决问题；
- 是否需要 Amendment。

# 8. 各工作包的具体分工

## 8.1 形式化研究问题

### 人类 MUST

- 决定研究为什么存在以及核心价值；
- 决定隐藏真实目标、合法变化和严重失败的含义；
- 承担因果主张与研究边界的责任；
- 选择最终采用的状态、本体和规范模型。

### Agent SHOULD

- 生成最小状态模型、版本化模型、状态机、因果图和接受集合等竞争方案；
- 查找循环定义、不可识别问题和反例；
- 将批准的概念转换为数学、DSL、Schema 和测试；
- 维护被拒绝方案登记表。

## 8.2 变更分类

### 人类 MUST

- 决定 `CAPABILITY_PATCH`、`EVALUATOR_PATCH`、`GOAL_DISCOVERY`、`GOAL_NORMATIVE_CHANGE`、`AUTONOMY_CHANGE`、`ASSURANCE_CHANGE` 的规范性边界；
- 决定授权关系和严重性；
- 对 Gold 边界案例作最终裁决。

### Agent SHOULD

- 生成大量正例、反例、边界案例和对抗性复合 Patch；
- 检查类别是否互斥、穷尽和可执行；
- 预分类并分析人类分歧，但不得替代 Gold 裁决。

## 8.3 H1–H3 与统计协议

### 人类 MUST

- 决定主要科学主张和主要比较；
- 决定非劣界限、安全阈值、排除规则和支持/否定条件；
- 在主实验前冻结确认性分析。

### Agent SHOULD

- 发现平凡假设、指标攻击和替代解释；
- 运行功效模拟、敏感性分析和统计代码测试；
- 建立“假设—Estimand—字段—脚本—结果表”的追溯矩阵。

## 8.4 数据结构与软件实现

### 人类 MUST

- 定义字段现实语义、权限、隐私、公开范围和历史失效要求；
- 验收完整 Fixture 是否符合研究原意。

### Agent SHOULD

- 生成 JSON Schema、DDL、类型、迁移、验证器、Fixture、属性测试、重放脚本和指标计算器；
- 自动发现字段缺失、版本错配、非法引用和不可重算结果。

## 8.5 实验运行

### 人类 MUST

- 批准主实验启动、冻结模型与预算、决定是否解封 Sealed Test；
- 对基础设施异常和方法失败的分类作预注册范围内的裁决。

### Agent SHOULD

- 自动编排运行、记录日志、计算成本、检测漂移和生成异常报告；
- 保留所有失败和中间快照；
- 在不读取密封内容的前提下检查流程完整性。

## 8.6 结果分析与论文

### 人类 MUST

- 对结论强度、现实含义、伦理边界和作者责任作最终判断；
- 确保不把探索性发现冒充确认性结论。

### Agent SHOULD

- 重算结果、生成图表、检查表格一致性、寻找反例和替代解释；
- 起草不同强度的结论措辞，并标明各自所需证据；
- 检查论文主张是否超出 Track A / Track B 的证据覆盖范围。

# 9. Agent 自治契约

## 9.1 Agent 可以自主执行

在任务边界和规范已冻结时，Agent 可以：

- 生成代码、测试、Schema、Fixture 和文档；
- 运行沙箱实验、模拟、Lint、单元测试和一致性检查；
- 执行可逆的重构；
- 生成候选和反例；
- 报告异常、风险和未解决问题；
- 维护版本、哈希和追溯矩阵。

## 9.2 Agent 只能提案、不得自行生效

以下事项必须形成明确的人类审批点：

- 新增、合并或修改变更类别；
- 修改研究形式化、本体或因果假设；
- 修改主要指标、Estimand、分母或非劣界限；
- 修改 Goal、Autonomy、Assurance 或 Capability Envelope；
- 修改 Gold 标签、专家量表或严重性定义；
- 修改样本排除、失败处理和多重比较规则；
- 扩大数据、工具、仓库或发布权限；
- 更换正式主实验使用的模型、提示词或预算。

## 9.3 Agent 禁止执行

Agent 不得：

- 根据正式结果调整 H1–H3，使结果更有利；
- 读取、推断或泄露密封测试和隐藏真实目标；
- 删除、隐藏或改写不利运行；
- 将方法失败标成基础设施失败以排除；
- 将探索性分析重新标成确认性分析；
- 自行修改 Gold 标签或专家裁决；
- 批准自己提出的规范性 Patch；
- 伪造批准、测试、引用、数据或完成状态；
- 宣称未实际完成的工作已经完成；
- 承诺在不可执行的后台流程中稍后交付结果。

# 10. 人类行为义务

人类拥有最终权力，也必须承担对应义务。

人类 MUST：

- 明确规范性决定由谁负责，不能把不愿承担的决定默默交给 Agent；
- 不因 Agent 输出流畅而跳过验证；
- 不以作者偏好选择性采用 Agent 的有利分析；
- 对拒绝或采纳 Agent 建议的关键理由形成记录；
- 保护 Experimental Agent 与隐藏资料之间的隔离；
- 在协议冻结后，不通过口头指令或临时代码绕过 Amendment；
- 对外承担作者、数据和风险责任。

# 11. 沟通与工作透明度

## 11.1 任务开始

Agent 应明确：

- 当前理解的目标；
- 已采用的关键假设；
- 将交付什么；
- 哪些点需要人类决定。

简单任务不必增加流程负担；复杂任务应提供简短的阶段说明。

## 11.2 工作过程

对持续较长或包含多步骤的任务，Agent 应提供少量、信息密度高的进度更新：

- 已完成的重要部分；
- 提前发现的风险或缺陷；
- 当前仍在验证的事项。

不得用低层操作日志淹没决策信息。

## 11.3 结果交付

Agent 的交付说明必须区分：

- **已完成且验证**；
- **已完成但未独立验证**；
- **推断或建议**；
- **未完成或证据不足**。

任何不确定性不得通过肯定语气隐藏。

# 12. 软件开发行为准则

## 12.1 任务与范围

- 每项代码修改必须关联 Work Order、Issue 或实验任务编号。
- 不得在修复一个问题时顺带进行未经批准的大范围重构。
- 发现相邻问题时，优先记录为独立任务。

## 12.2 分支与提交

- 正式代码不得直接在主分支上无审查修改。
- 提交应原子化，说明“为什么改”，而不仅是“改了什么”。
- 协议变化与普通实现变化应尽量分开提交和审查。
- 不得通过 Force Push 隐藏已经评审的历史，除非明确批准并保留记录。

## 12.3 Pull Request / 变更包

每个 PR 或正式变更包至少包含：

- 目标和范围；
- 关联协议/Issue；
- 变更类型；
- 测试；
- 数据和 Schema 影响；
- 安全与研究有效性风险；
- 回滚方法；
- 未解决问题；
- 是否改变确认性实验条件。

## 12.4 测试

- 新行为必须有正例、反例和至少一个边界测试。
- 修复缺陷时应先增加能复现缺陷的测试。
- Schema 修改必须有迁移和旧数据兼容性测试。
- 与 H1–H3 相关的核心指标必须有独立重算测试。
- 不得为了让 CI 通过而静默跳过关键测试。

## 12.5 依赖、密钥和环境

- 新依赖必须说明用途、版本和替代方案。
- 密钥、令牌、个人信息和企业敏感数据不得进入代码、提示词、日志或公开数据。
- 模型、提示词、工具、依赖和运行环境必须可追溯到具体版本。

# 13. 研究数据与实验行为准则

- 原始轨迹只追加，不覆盖；修正应生成新版本和理由。
- 原始事实、Agent 推断、人工标签和裁决结果必须分字段保存。
- 所有主要结果必须能从原始记录重新计算。
- Experience、Validation、Replay、ID、OOD 和 Sealed 数据必须明确分离。
- Experimental Agent 不得通过日志、错误信息或目录结构间接获取隐藏信息。
- 模型调用失败、超预算、工具异常和方法自身导致的错误必须分开记录。
- 任何排除必须匹配预注册规则，并保留排除前记录。
- Sealed Test 只在方法、提示词、指标和统计方案冻结后一次性解封运行。

# 14. 自动升级条件

出现以下任一情况，Agent 必须停止相关正式生效动作并升级给有权人类：

1. Patch 改变接受集合；
2. Patch 修改 Goal、Autonomy、Assurance 或 Capability Envelope；
3. 修改影响 H1–H3、主要指标、分母、非劣界限或排除规则；
4. 涉及隐藏目标、Gold 标签、专家裁决或密封测试；
5. 多个 Agent 或人类编码者对分类产生实质分歧；
6. Codebook 无法给出唯一类别；
7. 证据冲突且选择会影响结论；
8. 需要决定谁承担风险或谁有权授权；
9. 需要修改已冻结协议；
10. 发现可能改变论文主结论的新错误；
11. 发生隐私、版权、权限或密钥泄漏；
12. 无法确定修改是否可逆。

# 15. 事件与异常处理

## 15.1 严重事件

以下属于严重事件：

- 隐藏目标或密封数据泄漏；
- 未授权修改正式 Goal、指标或 Gold 标签；
- 删除或篡改失败运行；
- 伪造批准、测试或数据；
- 主实验在未记录的模型、提示词或配置下运行；
- Experimental Agent 获得不应访问的评估信息。

## 15.2 响应流程

1. 立即停止受影响运行或合并；
2. 保留现场、日志和哈希；
3. 标记受影响数据和产物；
4. 由独立人类和 Audit Agent 评估范围；
5. 决定回滚、重跑、降级为探索性或废弃；
6. 发布 Incident Record；
7. 修改流程或测试，防止复发。

不得通过覆盖日志或重新运行来掩盖首次事件。

# 16. 冻结与 Amendment

## 16.1 冻结层级

- **Draft**：可自由讨论和修改，不用于确认性结论。
- **Pilot Freeze**：用于工程试点；可因可执行性问题修改，但不得根据方法优劣选择修改。
- **Protocol Freeze**：主实验前冻结 H1–H3、指标、样本、模型、预算、排除和 Schema。
- **Sealed Freeze**：方法、提示词、代码和统计脚本均冻结，随后解封最终测试。

## 16.2 Amendment 必须记录

- 修改内容；
- 触发原因；
- 修改发生在看到哪些结果之前或之后；
- 对确认性结论的影响；
- 受影响数据和版本；
- 批准者；
- 是否需要重新运行；
- 新旧版本哈希。

冻结后修改产生的分析默认视为探索性，除非通过独立、事先未接触的数据重新确认。

# 17. 质量 Gate

## 17.1 进入实现前

- [ ] 目标、非目标和验收标准明确；
- [ ] 自治等级明确；
- [ ] 规范性决策点已分配给具体人类；
- [ ] 已列出至少一个可能失败方式；
- [ ] 涉及隐藏资料时已建立访问隔离。

## 17.2 进入主实验前

- [ ] H1–H3、主要比较和 Estimand 已冻结；
- [ ] 非劣界限、排除和失败处理已冻结；
- [ ] 模型、提示词、工具、预算和代码有哈希；
- [ ] 数据划分和 Sealed Test 已隔离；
- [ ] 指标可从原始数据自动重算；
- [ ] 失败和回归不会被静默丢弃；
- [ ] Audit Agent 与独立人类已完成审查。

## 17.3 合并或交付前

- [ ] 变更未超出 Work Order；
- [ ] 测试通过且未静默跳过；
- [ ] 文档、Schema 和代码一致；
- [ ] 风险和回滚已记录；
- [ ] 未把未验证内容声明为已验证；
- [ ] 文件与下载路径实际存在；
- [ ] 需要的人类批准已获得。

# 19. 评价人机合作本身

项目应定期评价协作机制，而不是只评价模型任务成绩。

建议指标：

- Agent 发现的人类遗漏的重要方案数；
- 冻结前发现的概念冲突和指标漏洞数；
- 人类推翻 Agent 建议的比例及原因；
- Agent 发现的人工协议或实现错误；
- 人类—人类、人类—Agent、Agent—Agent 分类分歧；
- Protocol Freeze 后实质 Amendment 数；
- Schema 无法表达事件的缺陷率；
- 主要指标自动重算率；
- 隐藏信息泄漏事件；
- 人类时间是否从机械工作转向关键判断；
- Agent 自动化是否减少返工，而不是将工作转移为纠错。

不得把“Agent 建议采纳率”作为主要成功指标，因为这会激励自动化偏见。

# 20. 冲突解决与优先级

出现冲突时按以下顺序处理：

1. 法律、伦理、数据权利和安全要求；
2. 已冻结的 Goal Contract 与研究协议；
3. 本协作宪章；
4. 已批准的 Work Order 与 Decision Record；
5. 工程便利、速度和成本；
6. Agent 或个人偏好。

当人类意见冲突时，应由预先指定的责任角色作出决定，并记录异议；不得让 Agent 通过选择某一方意见暗中成为最终裁决者。

# 21. 一页式默认行为准则

## 人类负责

- 定义目标、红线、授权与风险；
- 决定 H1–H3、阈值和研究结论；
- 对规范性变化和正式发布签字；
- 承担科学、数据和社会责任。

## Agent 负责

- 扩大候选空间；
- 生成反例和边界案例；
- 实现代码、Schema、测试和模拟；
- 检查一致性、追溯性和可重算性；
- 如实报告失败、不确定性和限制。

## 共同完成

- 形式化研究问题；
- 变更分类与边界案例；
- H1–H3 的操作化；
- 数据结构语义与完整 Fixture；
- 结果解释和替代解释分析。

## 永远禁止

- 同一主体独自定义、修改、评价并批准成功；
- Agent 自行改变目标、权限、证明、Gold 标签或确认性假设；
- 人类或 Agent 删除不利结果；
- 用流畅解释代替证据；
- 将未完成、未验证或探索性工作伪装成正式结论。
